# n8nローカル実行

## 前提

- Docker EngineとDocker Compose v2が利用できること
- リポジトリ直下にローカル専用の `.env` があり、十分に長いランダムな `N8N_ENCRYPTION_KEY` が設定されていること
- `.env` は作成・編集・コミットせず、利用者が安全な場所で管理すること

## 起動

設定の解決結果を確認してからn8nを起動する。

```bash
docker compose config
docker compose up -d
docker compose ps
```

ブラウザで `http://localhost:5678` を開き、初回管理ユーザーを作成する。

## ログとヘルスチェック

```bash
docker compose logs --tail=100 n8n
docker compose ps
```

Composeのhealthcheckはコンテナ内部の `http://127.0.0.1:5678/healthz` を確認する。起動直後は最大30秒の猶予を設ける。

## 停止

通常の停止ではnamed volumeを残す。

```bash
docker compose down
```

`docker compose down --volumes` はn8nの永続データを削除するため、バックアップと明示的な承認なしに実行しない。

## 永続化と再起動

- n8nデータはnamed volume `n8n_data` の `/home/node/.n8n` に保存する。
- コンテナは `unless-stopped` で再起動する。
- Credentialsは `N8N_ENCRYPTION_KEY` で暗号化される。同じデータを復元するには同じ鍵が必要となるため、GitHub以外の安全な保管先で管理する。
- workflow JSONはnamed volumeだけに依存せず、秘密情報を除外して `n8n/workflows/` へexportする。

## バックアップ

バックアップ対象は、n8nのnamed volume、Git管理中のworkflowとmigration、および別保管する `N8N_ENCRYPTION_KEY` である。鍵やcredentialの実値をバックアップ手順書やGitへ記録しない。

最初にComposeが使用しているvolume名を確認する。

```bash
docker volume ls --filter label=com.docker.compose.volume=n8n_data
docker volume inspect <確認したvolume名>
```

n8nへの書き込みを止め、Git管理外のバックアップ先へarchiveを作成する。

```bash
docker compose stop n8n
docker run --rm -v <確認したvolume名>:/data:ro -v <バックアップ先の絶対パス>:/backup alpine sh -c "tar czf /backup/n8n-data-backup.tar.gz -C /data ."
docker compose start n8n
```

作成後はSHA-256 checksum、取得日時、使用していたn8n image tagをバックアップ管理台帳へ記録する。`N8N_ENCRYPTION_KEY` はarchiveと別の安全な保管先で管理する。

## 復元

本番相当のvolumeへ上書きする前に、新しい空のvolumeを使って復元できることを確認する。既存volumeは削除しない。

```bash
docker volume create ai_mail_n8n_restore
docker run --rm -v ai_mail_n8n_restore:/data -v <バックアップ先の絶対パス>:/backup:ro alpine sh -c "tar xzf /backup/n8n-data-backup.tar.gz -C /data"
docker volume inspect ai_mail_n8n_restore
```

復元環境では、バックアップ時と同じ `N8N_ENCRYPTION_KEY` を実行環境から設定する。workflow一覧とcredential名を確認し、外部サービスへ接続する前に専用テスト環境で動作確認する。

## workflowのimportとexport

import前に、リポジトリ内のworkflowが構文・秘密情報検査を通ることを確認する。

```bash
node scripts/validate-repository.mjs
docker compose cp n8n/workflows/. n8n:/tmp/ai-mail-workflows/
docker compose exec n8n n8n import:workflow --separate --input=/tmp/ai-mail-workflows
```

import後はn8n UIで無効状態のままworkflowを開き、ノード構成、環境変数参照、credential未設定箇所を確認する。credentialはUIで割り当て、workflow JSONへ実値やcredential IDを追記しない。

UIで変更したworkflowは、まずGit管理外の一時ディレクトリへexportする。

```bash
docker compose exec n8n n8n export:workflow --backup --output=/tmp/ai-mail-workflows-export
docker compose cp n8n:/tmp/ai-mail-workflows-export/. <Git管理外のexport先>/
```

既存ファイルとの差分を確認し、credential ID、接続情報、実行データ、固定されていない環境依存IDを除外してから `n8n/workflows/` へ反映する。

## Supabase migrationの適用

`supabase/migrations/` をファイル名順に確認し、未適用のmigrationだけを専用テスト環境へ先に適用する。適用前に対象、影響範囲、ロールバック方法を確認し、適用済みmigrationは書き換えない。

Session poolerを利用する場合の実行例を示す。パスワードは接続URIへ埋め込まず、`psql` のpromptで入力する。

```bash
psql "host=<Session pooler host> port=5432 dbname=postgres user=<pooler user> sslmode=require" -f supabase/migrations/<未適用migration>.sql
```

適用後は対象table、制約、index、権限を確認する。本番相当環境への適用は、人間が専用テスト環境の結果をレビューした後に行う。

## credentialの登録

credentialの実値登録と疎通確認は人間がn8n UIで行う。共通契約は [n8n Credentials設定](20_n8n_Credentials設定.md) を確認し、サービス別の具体的な作業は次のHuman Issueに従う。

- Gmail: Issue #45

登録後も秘密情報をIssue、PR、スクリーンショット、ログへ貼らない。疎通確認には専用テストアカウントを使用する。

## 運用確認

起動、import、migration、credential登録後は次を確認する。

```bash
docker compose config
docker compose ps
docker compose logs --tail=100 n8n
node scripts/validate-repository.mjs
git status
git diff
```

- n8nがhealthyで、workflowが意図した有効・無効状態になっている
- importしたworkflowにcredentialや実行データが含まれていない
- migrationが一度だけ適用され、必要な制約が存在する
- ログやGit差分にAPIキー、token、password、個人情報が含まれていない
