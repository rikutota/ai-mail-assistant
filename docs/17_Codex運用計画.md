# Codex運用計画

## 1. Queue Engineeringの目的

GitHub Issueを小さく検証可能な作業キューへ分解し、Codexが1タスク・1PRで実装する。人間は優先順位、仕様判断、権限が必要な操作、最終承認に集中し、変更の追跡性とレビュー品質を保ちながら開発速度を高める。

## 2. キュー状態

| 状態 | 定義 | 次へ進む条件 |
| --- | --- | --- |
| Backlog | 未整理または優先順位待ち | 目的、範囲、優先度を人間が整理した |
| Ready for Codex | Codexが単独で着手できる | 受け入れ条件、対象、制約、確認方法が明確になった |
| In Codex | Codexが調査・実装・確認中 | PRを作成し、自己レビューが完了した |
| Review | 人間がPRを確認中 | 承認、または修正内容が具体化した |
| Needs Fix | 指摘への修正が必要 | Codexが修正と再確認を完了した |
| Ready to Merge | 承認と必須チェックが完了 | 人間がマージを判断した |
| Done | 基準ブランチへ反映済み | Issueが自動または手動でクローズされた |

状態変更はGitHub ProjectまたはIssueラベルで管理する。仕様が不足したタスクは無理に着手せず、Backlogへ戻して不足情報を記録する。

## 3. 役割分担

### Codexに任せる作業

- 既存コードとドキュメントの調査
- 範囲が明確な実装、バグ修正、テスト、ドキュメント更新
- n8n workflow JSONやSupabase migrationの作成・変更（Issueで明示され、安全な検証方法がある場合）
- lint、test、build、差分確認、秘密情報チェック
- ブランチ、コミット、PRの作成とレビュー指摘への修正

### 人間が行う作業

- プロダクト方針、優先順位、受け入れ条件の決定
- 曖昧な業務仕様、UX、セキュリティ、データ保持方針の判断
- Gmail / OutlookなどのOAuth同意、credential登録、本番環境の秘密情報設定
- 本番データを扱う操作、破壊的なDB変更、外部サービスへの公開・課金操作の承認
- PRの最終レビューとマージ、リリース判断

## 4. Codex投入タスクの粒度

1つのIssueは、原則として1つの目的を1つのPRで検証できる大きさにする。目安は対象領域が1つ、主要変更が数ファイル、確認方法が明確であること。実装、workflow、DB変更が独立してレビューできる場合は分割する。

次の場合は投入前に分割する。

- 複数の外部連携を同時に追加する
- 仕様決定と実装が混在する
- n8n、DB、UIなど複数領域へ大きくまたがる
- 受け入れ条件を短いチェックリストで表せない
- 失敗時に一部だけ安全に戻せない

## 5. Codex投入プロンプトの構成

投入プロンプトには次を含める。

1. 目的と背景
2. 作成・変更するファイル
3. 具体的な作業内容と受け入れ条件
4. 変更しない範囲と禁止事項
5. 秘密情報、互換性、データに関する制約
6. 実行する確認コマンドと期待結果
7. ブランチ名、コミットメッセージ、PRタイトルと本文
8. 関連Issue番号

既存仕様を推測させる表現は避け、参考にするドキュメントや期待する入出力例を示す。判断が必要な点は、投入前に人間が決めるか、質問事項として明記する。

## 6. 並列実行ルール

- 同じファイル、同じn8n workflow、同じDBテーブルを変更するタスクは並列にしない。
- 依存関係がある場合は、先行PRのマージ後に後続タスクをReady for Codexへ移す。
- 独立したdocs、テスト、別連携など、変更範囲が重ならないタスクのみ並列実行する。
- 各タスクに専用ブランチとPRを割り当て、1つの作業ディレクトリを複数タスクで共有しない。
- 競合が発生した場合は後続タスク側で基準ブランチを取り込み、確認をやり直す。

## 7. レビュー基準

- Issueの受け入れ条件をすべて満たしている
- 変更がIssueの範囲内で、不要な整形やリファクタリングがない
- 既存設計および関連docsと矛盾しない
- 正常系、主要な異常系、重複実行や再実行の影響が考慮されている
- 外部APIの失敗、レート制限、タイムアウト時に安全に処理できる
- n8n workflowにcredentialや実行データが含まれず、Supabaseの権限が過剰でない
- 必要なテストとドキュメントが更新され、確認結果がPRに記録されている

## 8. 秘密情報チェック

コミット前とPRレビュー時に次を確認する。

- APIキー、アクセストークン、refresh token、パスワード、秘密鍵がない
- `.env` が追加・変更されていない
- `.env.example` は変数名と明らかなダミー値だけである
- n8n workflow JSONにcredential ID、接続情報、メール本文、実行履歴がない
- ログ、スクリーンショット、テストfixtureに個人情報や本番データがない
- Supabase URLやキーなど、公開可否を判断していない値がない

秘密情報を発見した場合はPR作成を止める。値を差し替えるだけでなく、履歴からの除去とcredentialの失効・再発行を人間へ依頼する。

## 9. PR確認手順

1. `git status` で意図しないファイルがないことを確認する。
2. `git diff` とコミット差分を読み、Issue範囲、秘密情報、デバッグ出力を確認する。
3. タスク指定のlint、test、build、JSONまたはSQLの検証を実行する。
4. Markdownの見出し、表、コードブロック、相対リンクを確認する。
5. PR本文へ概要、変更内容、実行した確認と結果、未確認事項、`Closes #<番号>` を記載する。
6. CI結果を確認し、失敗があれば原因を修正して再確認する。
7. 人間がレビューし、承認後にReady to Mergeへ移す。
8. 人間がマージし、IssueのクローズとDoneへの移動を確認する。

## 10. Sprint 0でのCodexタスク一覧

Sprint 0では本実装の前提を、小さなキューとして整備する。各項目は原則として個別Issue・個別PRにする。

| 順序 | タスク | 主な成果物・完了条件 |
| --- | --- | --- |
| 1 | Codex運用ルールの追加 | `AGENTS.md`、本計画、READMEリンクを追加する |
| 2 | リポジトリ構成の確定 | n8n、Supabase、テストの配置方針をdocsに記載する |
| 3 | 環境変数一覧の整備 | 必要な変数名、用途、設定先を文書化し、`.env.example` はダミー値だけにする |
| 4 | CIの最小構成 | Markdown、JSON、SQLなど現時点で検証可能なチェックをPRで自動実行する |
| 5 | n8n workflow管理方針の具体化 | export / import、命名、credential除外、差分レビュー手順を定義する |
| 6 | Supabase migration基盤の整備 | migrationの命名、適用順、ロールバック、ローカル検証手順を定義する |
| 7 | テスト方針の具体化 | Gmail / Outlook取得、AI要約、通知、予定登録、重複防止の確認方法を定義する |
| 8 | 最初の縦切りタスクの準備 | Gmail取得からログ保存までを実装可能な粒度へ分解し、受け入れ条件を付ける |

各タスクは依存関係を明示し、前提が整ったものからReady for Codexへ移す。credentialの登録や本番接続はSprint 0のCodexタスクに含めず、人間が別途管理する。
