# エラー処理設計書

## 1. 概要

本ドキュメントでは、AIメールアシスタントにおけるエラー処理、リトライ、ログ保存、通知、復旧方針を定義する。

本システムは、Gmail、Outlook、OpenAI、Google Calendar、LINE、Supabaseなど複数の外部サービスに依存する。  
そのため、一部の処理が失敗しても、可能な限り他の処理を継続し、障害内容をログとして残す設計とする。

---

## 2. 基本方針

## 2.1 エラー処理の原則

- 一部サービスが失敗しても、可能な範囲で処理を継続する
- エラー内容は `error_logs` に保存する
- ユーザーが気づくべき重大エラーはLINE通知する
- APIキーやトークンなどの秘密情報はログに出力しない
- 同じメールが重複処理されないようにする
- カレンダー登録の重複を防ぐ
- 失敗したメールは後から再処理できる状態にする

---

## 2.2 エラー分類

| 分類 | 内容 |
|---|---|
| APIエラー | 外部API呼び出し失敗 |
| 認証エラー | OAuth、APIキー、トークン不正 |
| バリデーションエラー | 入力データやAI出力が不正 |
| DBエラー | Supabase保存・参照失敗 |
| 通知エラー | LINE通知失敗 |
| ワークフローエラー | n8nノード実行失敗 |
| データ不整合 | 重複、必須項目不足、想定外の値 |

---

## 3. エラー種別一覧

| error_type | 内容 | 重大度 |
|---|---|---|
| gmail_error | Gmail取得エラー | Medium |
| outlook_error | Outlook取得エラー | Medium |
| openai_error | OpenAI APIエラー | High |
| calendar_error | Google Calendar登録エラー | Medium |
| line_error | LINE通知エラー | High |
| supabase_error | Supabase保存・参照エラー | High |
| auth_error | 認証エラー | High |
| validation_error | データ検証エラー | Medium |
| duplicate_error | 重複処理関連エラー | Low |
| workflow_error | n8nワークフロー実行エラー | High |
| unknown_error | その他不明なエラー | Medium |

---

## 4. 重大度定義

| 重大度 | 意味 | 対応 |
|---|---|---|
| High | システム全体または主要機能が停止する | LINE通知、ログ保存、手動確認 |
| Medium | 一部機能が失敗するが処理継続可能 | ログ保存、通知本文に含める |
| Low | 運用上大きな影響がない | ログ保存のみ |

## 5. 外部サービス別エラー方針

## 5.1 Gmail取得エラー

### 想定エラー

- OAuthトークン期限切れ
- スコープ不足
- Gmail API制限
- ネットワークエラー
- メール本文取得失敗

### 対応方針

| 状況 | 対応 |
|---|---|
| Gmail一覧取得失敗 | Outlook処理は継続 |
| 一部メール詳細取得失敗 | 対象メールのみfailed扱い |
| 認証エラー | error_logs保存、LINEに重大エラーとして通知 |
| レート制限 | リトライ後、失敗時はログ保存 |

### error_type

```text
gmail_error
```

---

## 5.2 Outlook取得エラー

### 想定エラー

- Microsoft OAuthトークン期限切れ
- Microsoft Graph API権限不足
- Inbox取得失敗
- body取得失敗
- APIレート制限

### 対応方針

| 状況 | 対応 |
|---|---|
| Outlook一覧取得失敗 | Gmail処理は継続 |
| 一部メール取得失敗 | 対象メールのみfailed扱い |
| 認証エラー | error_logs保存、LINEに重大エラーとして通知 |
| レート制限 | リトライ後、失敗時はログ保存 |

### error_type

```text
outlook_error
```

---

## 5.3 OpenAI APIエラー

### 想定エラー

- API Key不正
- レート制限
- タイムアウト
- JSON形式不正
- モデル応答失敗
- 入力本文が長すぎる

### 対応方針

| 状況 | 対応 |
|---|---|
| API呼び出し失敗 | リトライ |
| リトライ後も失敗 | mail_logsにfailed保存 |
| JSONパース失敗 | validation_errorとして保存 |
| 出力形式不正 | 補正可能なら補正、不可能ならfailed |
| 本文が長すぎる | 本文を短縮して再実行 |

### error_type

```text
openai_error
```

### 注意

OpenAI APIに送信したメール本文全文は、原則としてDBに保存しない。

---

## 5.4 Google Calendar登録エラー

### 想定エラー

- OAuthトークン期限切れ
- スコープ不足
- 日時形式不正
- 過去日時
- イベント重複
- API呼び出し失敗

### 対応方針

| 状況 | 対応 |
|---|---|
| 登録失敗 | calendar_logsにfailed保存 |
| 日時不正 | カレンダー登録をスキップ |
| 認証エラー | error_logs保存 |
| 同一メールから登録済み | skipped扱い |
| Calendar失敗後 | LINE通知に失敗情報を含める |

### error_type

```text
calendar_error
```

---

## 5.5 LINE通知エラー

### 想定エラー

- Channel Access Token不正
- LINE_USER_ID不正
- Push Message失敗
- メッセージ本文が長すぎる
- API制限

### 対応方針

| 状況 | 対応 |
|---|---|
| LINE通知失敗 | notification_logsにfailed保存 |
| Token不正 | error_logs保存 |
| 本文が長すぎる | 通知文を短縮して再送 |
| 再送失敗 | n8n実行ログとerror_logsで確認 |

### error_type

```text
line_error
```

### 注意

LINE通知そのものが失敗した場合、ユーザーが気づきにくいため、Supabase上のログ確認を前提とする。

---

## 5.6 Supabaseエラー

### 想定エラー

- DB接続失敗
- API Key不正
- SQLエラー
- 制約違反
- 一意制約違反
- RLS設定不備
- タイムアウト

### 対応方針

| 状況 | 対応 |
|---|---|
| 重複判定失敗 | 安全側に倒して処理を停止 |
| mail_logs保存失敗 | n8n実行ログに記録 |
| error_logs保存失敗 | n8n標準ログで確認 |
| 一意制約違反 | 重複処理として扱う |
| DB接続失敗 | リトライ |

### error_type

```text
supabase_error
```

## 6. 処理継続方針

## 6.1 継続するケース

以下の場合は、ワークフロー全体を停止せず、可能な処理を継続する。

| エラー | 継続方針 |
|---|---|
| Gmail取得失敗 | Outlook処理は継続 |
| Outlook取得失敗 | Gmail処理は継続 |
| 一部メールのOpenAI処理失敗 | 他メールの処理は継続 |
| 一部メールのCalendar登録失敗 | 他メールの登録は継続 |
| 一部メールのDB保存失敗 | 他メールの処理は継続 |

---

## 6.2 停止するケース

以下の場合は、処理の安全性を優先し、ワークフローを停止または主要処理を中断する。

| エラー | 停止理由 |
|---|---|
| Supabase重複判定が全件失敗 | 重複通知・重複登録の危険がある |
| OpenAI API Key不正 | 主要処理が実行できない |
| LINE Token不正 | 通知不能 |
| n8n Credentials復号失敗 | 認証情報が使えない |
| 設定値不足 | 正常処理不能 |

---

## 7. リトライ設計

## 7.1 リトライ方針

一時的な障害が想定されるAPIについてはリトライする。

| 対象 | リトライ回数 | 間隔 | 備考 |
|---|---:|---:|---|
| Gmail API | 3回 | 5秒 | 一時障害・レート制限 |
| Microsoft Graph API | 3回 | 5秒 | 一時障害・レート制限 |
| OpenAI API | 2回 | 10秒 | レート制限・タイムアウト |
| Google Calendar API | 2回 | 5秒 | 重複登録に注意 |
| LINE Messaging API | 2回 | 5秒 | 本文長すぎの場合は短縮 |
| Supabase | 3回 | 5秒 | DB接続エラー |

---

## 7.2 リトライしないケース

以下はリトライしても改善しにくいため、即時エラー扱いとする。

| エラー | 理由 |
|---|---|
| 400 Bad Request | リクエスト内容が不正 |
| 401 Unauthorized | 認証情報不正 |
| 403 Forbidden | 権限不足 |
| JSON Schema不一致 | 出力形式の問題 |
| 必須項目不足 | データ不備 |
| 一意制約違反 | 既に処理済み |

---

## 7.3 HTTPステータス別対応

| ステータス | 意味 | 対応 |
|---|---|---|
| 400 | リクエスト不正 | ログ保存、リトライしない |
| 401 | 認証エラー | ログ保存、認証情報確認 |
| 403 | 権限不足 | ログ保存、スコープ確認 |
| 404 | 対象なし | スキップまたはログ保存 |
| 409 | 競合 | 重複として扱う |
| 422 | 入力不正 | バリデーションエラー |
| 429 | レート制限 | リトライ |
| 500 | サーバーエラー | リトライ |
| 502 | Gateway Error | リトライ |
| 503 | 一時利用不可 | リトライ |
| 504 | タイムアウト | リトライ |

## 8. バリデーションエラー設計

## 8.1 正規化メールの検証

AI処理前に、正規化済みメールオブジェクトを検証する。

### 必須項目

| 項目 | 必須 |
|---|---|
| source | YES |
| messageId | YES |
| subject | NO |
| senderEmail | NO |
| body | NO |
| receivedAt | YES |

---

## 8.2 バリデーションルール

| 条件 | 対応 |
|---|---|
| sourceがgmail/outlook以外 | failed |
| messageIdが空 | failed |
| bodyが空 | 件名のみでAI処理、またはother分類 |
| receivedAtが不正 | 現在時刻で補完、またはfailed |
| subjectが空 | `(件名なし)` を設定 |
| senderEmailが空 | null許容 |

---

## 8.3 AI出力の検証

OpenAI APIの応答後、以下を検証する。

| 項目 | 条件 | 不正時の対応 |
|---|---|---|
| summary | 文字列 | 件名から補完 |
| priority | High / Medium / Low | Mediumに補正 |
| category | 定義済みカテゴリ | otherに補正 |
| requiresAction | boolean | falseに補正 |
| isSchedule | boolean | falseに補正 |
| confidence | 0.0〜1.0 | 0.5に補正 |
| event | object / null | 不正ならnull |
| startDateTime | ISO 8601 | 不正ならisSchedule=false |

## 9. 重複処理エラー

## 9.1 重複判定キー

```text
source + message_id
```

---

## 9.2 一意制約違反時の扱い

`mail_logs` への保存時に一意制約違反が発生した場合、そのメールは既に処理済みと判断する。

### 対応

- `duplicate_error` としてログ保存
- LINE通知には原則表示しない
- Calendar登録は行わない

---

## 9.3 Calendar重複登録防止

同一メールから複数回Calendar登録しないよう、`calendar_logs` を確認する。

### 判定

```sql
select id
from calendar_logs
where mail_log_id = $1
  and status = 'created'
limit 1;
```

## 10.2 ログに含める情報

- ワークフロー名
- ノード名
- 対象サービス
- 対象メールID
- エラー種別
- エラーメッセージ
- 発生日時

## 10.3 ログに含めない情報

以下はログに出力しない。

- DB Password
- Authorization Header
- Cookie
- メール本文全文
- 個人情報を含む詳細本文

## 14. 再処理方針

## 14.1 再処理対象

以下は再処理対象とする。

- `processed_status = pending`
- `processed_status = failed`
- OpenAI API失敗
- Calendar登録失敗
- 一時的なAPI障害

---

## 14.2 再処理しない対象

以下は再処理しない。

- 重複処理済み
- バリデーション上明らかに不正
- messageIdが取得できないメール
- 過去日時の予定メール
- confidenceが低すぎる予定候補

---

## 14.3 MVPでの扱い

MVPでは自動再処理機能は実装しない。

Supabase上でfailedログを確認し、必要に応じて手動で再実行する。

---

## 15. 障害復旧手順

## 15.1 Gmail / Outlook取得失敗

1. n8n Credentialsを確認する
2. OAuthトークンを再認証する
3. APIスコープを確認する
4. 手動実行でメール取得を検証する
5. error_logsを確認する

---

## 15.2 OpenAI失敗

1. API Keyを確認する
2. 利用上限を確認する
3. モデル名を確認する
4. 入力本文の長さを確認する
5. JSON出力形式を確認する

---

## 15.3 Calendar登録失敗

1. Google Calendar Credentialを確認する
2. `calendar.events` スコープを確認する
3. 日時形式を確認する
4. 同一メールから既に登録済みでないか確認する
5. calendar_logsを確認する

---

## 15.4 LINE通知失敗

1. Channel Access Tokenを確認する
2. LINE_USER_IDを確認する
3. Push Message APIを単体でテストする
4. 通知本文の長さを確認する
5. notification_logsを確認する

---

## 15.5 Supabase保存失敗

1. DB接続情報を確認する
2. Supabase API Keyを確認する
3. テーブルが作成済みか確認する
4. CHECK制約違反を確認する
5. error_logsまたはn8n実行ログを確認する

---
